# ADR 0002: Sign-in

Status: Accepted for Sprint 0. Built against the API contract and a mock, not yet against a live Google sign-in (see Consequences).

## Context

The Go API signs people in with Google (`/auth/google/login`), stores a JWT in an HttpOnly cookie named `room_auth`, and answers `/api/v1/auth/me` and `/api/v1/auth/logout`. Roles are `USER_A`, `USER_B`, `OS` and `ADMIN`. The login design shows a CUNET username and password form, which the API does not support (open question 2).

The cookie is set with `Path=/api/v1`. The browser therefore sends it only to `/api/v1/...` URLs. It is never sent when the browser asks Next.js for a page such as `/os`, so server components and middleware cannot see who is signed in.

## Decision

| Area         | Choice                                                                                                                 | Why                                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| API access   | `next.config.js` rewrites `/api/v1/*` and `/auth/google/*` to `API_BASE_URL`                                           | The cookie becomes first-party to this site, with no CORS. The Google redirect URL can point at this site |
| Route guard  | `AuthGate` in the `(user)` and `os` layouts calls `/api/v1/auth/me` in the browser and renders nothing until it passes | The server cannot see the cookie (see Context)                                                            |
| Roles        | `canAccess` in `src/domain/auth.ts`: OS pages need `OS`, user pages need `USER_A` or `USER_B`, `ADMIN` gets both       | Mirrors the API's `RequireRoles`. Anyone sent to the wrong area is redirected to their own home           |
| After login  | The API redirects to `/`. `/` sends people to the page they wanted, or to `/os` or `/home`                             | The API cannot carry a "next" page, so it is kept in `sessionStorage`                                     |
| Login screen | One "Sign in with Google" button replaces the username and password form                                               | The API has no password sign-in                                                                           |
| Sign out     | Account menu in the page header calls `/api/v1/auth/logout`, clears the query cache and goes to `/login`               | Open question 24                                                                                          |
| Data access  | Auth calls use `fetch` from the browser, not tRPC                                                                      | tRPC runs on the server, which never receives the cookie. This is an exception to the AGENTS.md rule      |

## Consequences

- The gate is a convenience, not security. Hiding a page in the browser does not protect data. Real protection must be in the API, and the sheet-booking endpoints are public today (see the API README). All screens that load private data must get it from endpoints that check the cookie.
- Each protected page flashes "checking sign-in" before it shows. If the API moved the cookie to `Path=/`, a Next.js middleware could redirect on the server instead and the flash would go.
- Set `GOOGLE_REDIRECT_URL` and `FRONTEND_URL` in the API to this site's address when deploying, and keep `AUTH_COOKIE_SAME_SITE=lax`.
- Local sign-in needs the API to run with `DATABASE_URL`, `JWT_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` set. When they are not set, `/api/v1/auth/me` does not exist, and every protected page shows "cannot check sign-in" with a retry button.
- The flow was tested against a mock of the API's auth contract. A real Google round trip has not been tested yet.
