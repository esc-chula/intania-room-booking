# ADR 0002: Sign-in

Status: Accepted for Sprint 0. The browser calls the API directly, as the API team designed it. "Proxy mode" is an optional variant for when the site and the API cannot share a parent domain. See "History" for the first proxy design and why it was dropped.

## Context

The Go API signs people in with Google (`/auth/google/login`), stores a JWT in an HttpOnly cookie named `room_auth`, and answers `/api/v1/auth/me` and `/api/v1/auth/logout`. Roles are `USER_A`, `USER_B`, `OS` and `ADMIN`. The login design shows a CUNET username and password form, which the API does not support (open question 2).

The API's cookies are host-only. The temporary OAuth state cookie and `room_auth` both belong to the API's own host, and `room_auth` is set with `Path=/api/v1`. Google returns the browser to the API's `GOOGLE_REDIRECT_URL`, so login only works when the browser started it on that same host. The API's own docs say the frontend must use the `GOOGLE_REDIRECT_URL` origin for login and for authenticated API requests.

Pages are never sent the cookie, so server components and middleware cannot see who is signed in.

## Decision

| Area         | Choice                                                                                                                                     | Why                                                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| API access   | The browser calls the API at `NEXT_PUBLIC_API_BASE_URL` with `credentials: "include"` (`src/lib/api.ts`). There are no rewrites to the API | The cookies belong to the API's host. The API allows it with credentialed CORS for its `FRONTEND_URL` origin            |
| Login        | The button is a full page load to `<API>/auth/google/login`                                                                                | The state cookie is set on the API host, and Google returns the browser to the same host                                |
| Route guard  | `AuthGate` in the `(user)` and `os` layouts calls `<API>/api/v1/auth/me` in the browser and renders nothing until it passes                | The server cannot see the cookie (see Context)                                                                          |
| Roles        | `canAccess` in `src/domain/auth.ts`: OS pages need `OS`, user pages need `USER_A` or `USER_B`, `ADMIN` gets both                           | Mirrors the API's `RequireRoles`. Anyone sent to the wrong area is redirected to their own home                         |
| After login  | The API redirects to `FRONTEND_URL` (`/`). `/` sends people to the page they wanted, or to `/os` or `/home`                                | The API cannot carry a "next" page, so it is kept in `sessionStorage` on this site                                      |
| Login screen | One "Sign in with Google" button replaces the username and password form                                                                   | The API has no password sign-in                                                                                         |
| Sign out     | Account menu in the page header calls `<API>/api/v1/auth/logout`, clears the query cache and goes to `/login`                              | Open question 24                                                                                                        |
| Data access  | Calls that need the cookie (auth and the sheet bookings) use `fetch` from the browser with React Query hooks, not tRPC                     | tRPC runs on this site's server, which never receives the API's cookie. This is an exception to the AGENTS.md data rule |

## Settings that must agree

| Setting                    | Where             | Value                                                                                                          |
| -------------------------- | ----------------- | -------------------------------------------------------------------------------------------------------------- |
| `GOOGLE_REDIRECT_URL`      | API               | `<API origin>/auth/google/callback`, also registered in Google Cloud Console                                   |
| `NEXT_PUBLIC_API_BASE_URL` | this app (Vercel) | The same `<API origin>`                                                                                        |
| `FRONTEND_URL`             | API               | This site's origin. It is the redirect after login and the only origin CORS allows                             |
| `AUTH_COOKIE_SAME_SITE`    | API               | `none` when this site and the API are on different sites (the production default), `lax` for local development |

## Consequences

- The gate is a convenience, not security. Hiding a page in the browser does not protect data. Real protection is in the API, which checks the cookie on the sheet endpoints.
- Each protected page flashes "checking sign-in" before it shows.
- If this site and the API are on different sites (for example `*.vercel.app` and `*.run.app`), the cookie is a third-party cookie. Some browsers block those, notably Safari, so signing in can succeed and `/api/v1/auth/me` still answer 401. Putting both under one parent domain (such as `booking.example.org` and `api.example.org`) avoids it. This is open question 30 and has not been tested on Safari yet.
- Only the API's `FRONTEND_URL` origin is allowed by CORS. Vercel preview deployments have other origins, so they cannot sign in or read bookings.
- `NEXT_PUBLIC_API_BASE_URL` is built into the app, so changing it needs a new deployment.
- Local sign-in needs the API to run with `DATABASE_URL`, `JWT_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` set. When they are not set, `/api/v1/auth/me` does not exist, and every protected page shows "cannot check sign-in" with a retry button.

## Proxy mode (no shared domain)

Direct calls make the API's cookie a third-party cookie when the site is on `*.vercel.app` and the API on `*.run.app`. Safari, every browser on iOS, incognito windows and Chrome with third-party cookies blocked do not send it, so sign-in completes and `/api/v1/auth/me` still answers 401 (`invalid authentication cookie`). Open question 30 is the clean fix (one parent domain). When there is no domain, proxy mode makes the cookie first-party instead:

- `API_PROXY_TARGET` (server variable, set only in production) is the API's real origin. `next.config.js` then rewrites `/api/v1/*` and `/auth/google/*` to it (`src/lib/api-proxy.js`).
- `NEXT_PUBLIC_API_BASE_URL` is this site's own origin, so `apiFetch` and the login button call the site, and the site forwards them. The code does not change; only these settings do.
- The API's `GOOGLE_REDIRECT_URL` is `<this site>/auth/google/callback`, also registered in Google Cloud Console. Login starts on this host, so the OAuth state cookie is set on it, and Google returns the browser to the same host. This is what the first proxy design got wrong. `FRONTEND_URL` stays this site's origin, and the API sees the same-site requests it already allows.
- `AUTH_COOKIE_SAME_SITE` can be `lax`, because every request is same-site.

| Setting                    | Direct (default)                    | Proxy mode                              |
| -------------------------- | ----------------------------------- | --------------------------------------- |
| `API_PROXY_TARGET`         | unset                               | The API's origin (`https://...run.app`) |
| `NEXT_PUBLIC_API_BASE_URL` | The API's origin                    | This site's origin                      |
| `GOOGLE_REDIRECT_URL`      | `<API origin>/auth/google/callback` | `<this site>/auth/google/callback`      |
| `AUTH_COOKIE_SAME_SITE`    | `none`                              | `lax`                                   |

Costs: each API call takes an extra hop through Vercel, and only the one origin that is registered with Google can sign in (previews cannot, as before). Local development stays direct: leave `API_PROXY_TARGET` unset.

## History

The first version of this ADR proxied the API through Next.js rewrites (`/api/v1/*` and `/auth/google/*`), so the cookie would be first-party to this site and the Google redirect URL would point at this site. That contradicted how the API issues its cookies. The login started on this site's host, so the OAuth state cookie was set there, while Google returned the browser to the API's host, which had no state cookie. Every sign-in ended with `auth_error=invalid_callback`. A later variant served tRPC under `/api/v1/trpc` to forward the cookie from the server. Both were replaced with direct calls from the browser, which is the flow the API was built for.
